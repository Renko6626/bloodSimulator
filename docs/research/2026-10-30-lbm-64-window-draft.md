# 64×64 LBM窗口后续实验草案

2026-10-30。用户允许记录为后续实验草案；**未实施、未运行、未安排云实例**。本轮正式区块系统使用16单位地图网格和原3×3＝48×48 LBM。此文不构成启动实验授权。

## 要回答的问题

64×64（4×4个16单位块）能否扩大局部反馈与相机活动余量，同时保持可接受的整帧成本？覆盖更大范围不保证物理更准确；窗口变化也可能遇到当前算法不支持的弯曲/分叉/角点开口。

## 可直接计算的规模

| 同一格距下 | 48×48 | 64×64 |
| --- | ---: | ---: |
| Fine格距 | 0.25 | 0.25 |
| Fine格子数 | 192²＝36864 | 256²＝65536 |
| Coarse格子数 | 96²＝9216 | 128²＝16384 |
| 每个全格点数组规模比 | 1 | 16/9≈1.778 |

主要格点计算、分布数组和全场读回字节预计随格数增加约78%；这不等于流体耗时或整帧耗时必定增加78%。GPU占用、带宽、同步等待、移窗准备和耦合数量均需同轮实测。格距、黏度和速度预算不变时，空间范围本身不要求增加格子子步。

## 实验前必须确定

- 偶数4×4窗口相对玩家的定位。不能只把WINDOW_BLOCKS从3改4，仍沿用原偏向位置而声称居中；中心诊断中的n/3和三分区假设也需核对。
- 先保持16单位迁移步幅，单独比较窗口面积；若之后要试32单位迁移，另做独立对照，不能把两种改动混为收益。
- 64窗口和迁移目标需由5×5现场覆盖并留足身体/耦合支持。按实际边界检查；不要为整齐自动扩大实体种群。
- 原53.3单位宽画面能否全覆盖取决于定位与迁移偏移。若以16单位网格就近对齐窗口中心，到最近边最少约24单位，仍不足以保证半宽26.7全部覆盖。当前zoom2画面宽约26.7，更容易覆盖。
