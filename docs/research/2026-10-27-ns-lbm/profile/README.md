# Vast CPU NS profile

2026-10-27。目标、观测范围见 [计划](plan.md)。本轮由用户指定 Vast 主机执行，实例 57949215；消费 GPU 为 RTX 3060 12GB，CPU 为 Xeon E5-2683 v4。CPU NS 未包含 GPU kernel，本批测量 CPU 推进、线程与数值求解，GPU 设备状态另存用于后续 LBM 实验。

## 测量方法

原始首批 release 二进制作为 baseline；新二进制只添加可关闭观测和可配置 Rayon 线程数，没有更换对流、投影、黏性或耦合算法。保持 72 细胞、每帧两个 1/120 s 子步、48×48 完整域、同初态／驱动。每组热身 30 帧，记录 120 帧，两轮反序。192² 与 256² 分别测试 baseline、off4、detail4、off1、detail1。off/detail 是观测关闭／打开，数字为 Rayon 工作线程数；faer 始终 Par::Seq。固定 CPU 2–5，不改变主机频率策略。

细分计时用墙钟、全进程 CPU 时钟与主线程 CPU 时钟，分别覆盖耦合、对流、驱动、两个速度黏性求解、压力 RHS／求解／速度修正、Rapier 和诊断。全进程 CPU 时间包含所有线程执行／自旋，不能把它和墙钟之差直接称为等待时间。整步 p95 取逐帧观测，不由阶段 p95 相加。

perf 权限在本机及云端都受限；云端直接调用自进程 user-space perf_event_open 的探针返回 EPERM。没有改宿主内核参数。使用 [sample.c](sample.c) 为主线程和 Rayon 工作线程创建按线程 CPU 时间运行的定时器，每约 2 ms 记录当前指令地址、TID 与阶段。只记录测量区，排除初始化／热身；采样另跑各 240 帧。采样组不用于预算验收。

这是 self-PC 采样，不是完整调用栈／火焰图。定时器受系统分辨率和信号合并影响，overrun 数量单独保存；热点占比只用于定位，不能等同精确函数耗时。没有硬件 cycles、instructions、cache-misses，就不下 IPC 或内存带宽实测结论。地址按归档 ELF 的 PT_LOAD 段与对应 maps 转换，再由 addr2line 定位；不假设虚拟地址等于文件偏移。

## 结果与判断

**当前超时主要来自插值／索引算术和预分解后的数值求解。云端复测重现了超预算，原服务器的等待尖峰不能单独解释这些成本。**

原始二进制 baseline、72 细胞、每帧两个子步，两轮合计各 240 帧：

| 完整网格 | 整步 mean / p95 ms | 流体+耦合 mean / p95 ms |
| --- | ---: | ---: |
| 192² | 68.63 / 72.61 | 64.32 / 68.14 |
| 256² | 118.43 / 133.64 | 113.52 / 128.39 |

下面是 detail4 两轮的分段平均，每行均为一个 1/60 s 周期的累计墙钟，不是单个子步。它用于解释成本，不替代未观测组的性能结果。

| 阶段 | 192² ms | 256² ms |
| --- | ---: | ---: |
| 对流 | 19.93 | 35.01 |
| u 黏性求解 | 13.93 | 27.73 |
| v 黏性求解 | 13.50 | 26.84 |
| 压力求解 | 13.63 | 27.49 |
| 压力 RHS 与速度修正 | 2.40 | 4.27 |
| 细胞交换 | 0.24 | 0.25 |
| Rapier | 3.56 | 3.83 |
| 驱动与诊断 | 0.86 | 1.49 |

### 对流：先查权重与边界索引计算

192²／256² 的对流阶段分别收集 9,546／16,471 个样本。`grid::weights` 占 69.6%／71.0%，`floor` 占 7.6%／7.7%，速度采样外层约 9.0%／8.3%。对流阶段的 `sched_yield` 仅占约 0.8%／0.3%，结合阶段 CPU 计时，不支持“主要花在 Rayon 等待”的解释。

每个速度输出点的 RK2 回溯需要五次标量采样；每次都重走通用权重、周期与壁反射分支。二进制反汇编确认 weights 函数包含重复除法、取整、整除／余数和边界分支。整个函数约 756 条静态指令，包含不同边界与整数宽度路径，不能把全部指令数当成每次调用实际执行数。指令地址附近的采样也不是精确 PMU 延迟归因，不能宣称每条 div 的周期贡献。

值得优先做的局部实验是：减少不变格距计算、重复坐标／权重运算，专门检查内域与边界通用路径的成本，再验证是否保持原边界插值与物理误差。本轮只定位，未改变近壁插值模型或实现更高阶对流。

### 求解：时间确实消耗在已有因子上

u 黏性、v 黏性、压力三项累计约 41.06／82.06 ms，占细分周期约 60.3%／64.7%。每个周期两个子步，实际执行六次线性系统求解；初始化与重新分解不在这些计时内。

求解样本集中在 faer supernodal Cholesky 的矩阵向量乘（各阶段约 45.6%–54.0%）、三角回代（约 15.3%–17.3%）及 supernode 遍历／集散。可以看到 `pulp::x86::v3::V3` 向量化内核，不能简单归因成“全部落入标量通用代码”。主线程 CPU 时间几乎等于求解墙钟，进程总 CPU 也接近单线程值，与 `Par::Seq` 一致。

这证明当前路径主要在执行求解工作，不能进一步区分计算吞吐与缓存／内存停顿；本轮没有硬件计数器。数值因子大小约 38.9／75.0 MiB，不等同于实际内存流量，不能据此计算带宽。

只消除压力开销不够，两个黏性求解和对流本身均超过预算。如果保留 CPU 路线，下一次应将三个系统放入同一组数值等价的 microbenchmark，先研究已有 faer 路径的适配性，再讨论不同线性算法。FFT、多重网格或 GPU NS 留待下一轮方案确认。

### 线程、耦合与观测开销

四线程对流的进程 CPU／墙钟约为 3.96，主线程只消耗约 0.04 ms／帧，工作实际在 Rayon 线程执行。关闭观测的整步平均：四线程约 68.99／122.53 ms，单线程约 177.37／269.37 ms；改成单线程没有收益。

各组的串行求解时间也发生变化：192² 单线程组约 23–25 ms／项，四线程组约 13–14 ms／项。faer 在两组都顺序求解，这不能解释成 faer 并行加速。动态频率、线程迁移及缓存状态仍是潜在干扰；本轮未锁频、未绑定每个工作线程，不能把比值当成纯算法加速比。一次频率快照同时出现约 1.2 GHz 与 2.67 GHz，但不足以归因每一帧。

细胞交换约 0.24／0.25 ms，Rapier 约 3.56／3.83 ms。Rapier 内部有软体约束求解和调度样本，但它不是超出 16.67 ms 的主要原因。

192² 的 detail4 与 off4 均值差约 -1.4%，256² 约 +3.6%；新 off4 与旧 baseline 分别差约 +0.5%／+3.5%。两轮 256² off4 自身也从 118.04 到 127.03 ms，噪声／运行状态不可忽略。不能把负差称为插桩加速，也不能精确扣除常量作为观测开销。采样组只用于定位。

CPU 配额为 15.36 核，期间 cgroup `nr_throttled` 和 `throttled_usec` 均未增加，没有发现本批被 CPU 配额限流的证据。共享主机与频率变化仍存在。

## 验证结果

- 原始 baseline 与全部线程／观测组，以及采样组前 120 个测量帧的九项已序列化物理观测值逐项相等。旧 baseline 没有完整流场指纹，不声称旧／新整场位级相等。
- 新二进制所有同长度组的末态速度场指纹一致：192² `37ac2c620bbedbab`，256² `8ec80e8a9e3eeb40`。这是 FNV 位模式检查，另有物理观测交叉核对，不是安全散列。
- 云端 18 个解析工况 JSON 与前一轮本地值完全相等，未改变此前涡流耗散结论。
- 两采样组各创建 5 个计时器，0 创建失败、0 缓冲溢出，各 2 次活动阶段 overrun；共 44,601 个样本，未解析函数符号 26 个。原始 PC、TID、maps、精确 ELF 与统计保留。
- 原有 lab 四项测试通过，Rust 格式、C 编译警告、Python 语法及差异检查通过。没有重跑游戏／UI。

## 建议的下一步顺序

1. 对权重／索引算术做局部等价优化实验，以既有边界、动量交换和解析误差为约束。
2. 并列研究两个黏性与压力求解的固定因子吞吐，不能只围着压力优化；改变线性算法前先比较方案和取舍。
3. 保留此基线进入已规划的 GPU LBM 对照。当前 CPU 原型距预算较远，不宜无期限优化；GPU LBM 仍须按相同物理时间、细胞交换与精度比较。

以上为后续建议，本次未更换数值算法、生产模块边界或默认游戏后端。
