# Vast.ai RTX 3060：冻结输入回放

2026-10-27，按用户提供的 SSH 入口连接并执行。实例为 Ubuntu 24.04.4 容器，RTX 3060 12GB、NVIDIA 580.65.06，wgpu 实际使用 Vulkan 物理 GPU。宿主 CPU 为双路 Xeon E5-2683 v4，64 个可见逻辑线程；cgroup 配额 `1536000/100000`，约 15.36 个逻辑核，内存上限约 60.4 GiB。不能将可见线程数当作独占 CPU 数。

## 方法与来源

本机从 `f3aaa4f` 对应的未改动源码构建 Linux x64 release `fluid-bench --features gpu`，Rust 1.98.1。上传预编译程序、源码快照和冻结 Linux 数据；实例上没有安装 Rust 或重新编译。二进制和输入均在运行前核对 SHA256。

三个规模、两个区域，每域前四个 RHS、两轮正反序。restart=32、max-iter=200、rtol=1e-4，比较 CPU LU、CPU FGMRES-MG 的 1／2 次 V-cycle、GPU FGMRES-MG 的 1／2 次配置。CPU LU 每条计时平均十次回代，其他后端每条一次。循环数和后端交错，第二轮反转区域／后端顺序。

probe、已知解 smoke 和全部 240 条回放记录通过，其中 GPU 为 96 条，两个循环配置各 48 条。计时不含设备／层次初始化，不含 Rapier、Godot 和范围调度。实际实验持续约 64 秒；本轮 cgroup 的 `nr_throttled` 和 `throttled_usec` 增量均为零，未出现配额节流。宿主仍可能有其他租户，未固定 CPU 亲和性、GPU 频率或做时间戳 profiling。

**跨平台输入更正：** 本轮原始 manifest 的 `options.input` 曾将冻结 Linux 输入误标为与 Windows 全部逐字节一致。实际核对显示：18 个矩阵文件、12 个初始 RHS／LU 向量全部一致；78 个后续动态向量有 6 个一致、72 个哈希不同。缺少 Windows 完整向量，未判断数值差幅度或原因。原始记录保留，详见[输入审计](validation/vast-rtx3060/input-audit.json)。本轮内部所有后端使用完全相同的冻结文件，同机比较有效；不以全部样本的跨机比值声称纯硬件加速。

## 结果

每格为两域两轮共 16 条记录的算术平均，单位 ms：

| 规模 | CPU LU | CPU MG 一次 | CPU MG 两次 | GPU MG 一次 | GPU MG 两次 |
| --- | ---: | ---: | ---: | ---: | ---: |
| small64 | 0.774 | 29.133 | 45.932 | 57.111 | 76.512 |
| wide96 | 0.599 | 92.748 | 124.143 | 95.285 | 126.777 |
| wide192 | 3.853 | 416.381 | 539.528 | 124.274 | 177.226 |

GPU 一次配置的迭代数依次为 17–18、36–51、38–57；两次配置为 15–16、32–42、34–46。均通过原始 f64 方程的全残差、相对动量 RMS 和连续性 RMS 检查，门槛维持 1e-4。两次循环降低迭代数，却增加本轮总耗时，说明迭代数不能独立代表成本。

同机 GPU 一次配置仍比 LU 慢约 74／159／32 倍。GPU 在 wide192 上优于当前 CPU 迭代实现，但后者使用 f64，不能将其视为隔离硬件的对照。当前固定矩阵复用因子的场景继续保留 CPU LU 默认。

## 现有计时能说明什么

| 规模／GPU 配置 | 总耗时 ms | 回读函数累计 ms | 回读函数之外 ms |
| --- | ---: | ---: | ---: |
| small64 一次 | 57.111 | 20.632 | 36.479 |
| small64 两次 | 76.512 | 25.921 | 50.592 |
| wide96 一次 | 95.285 | 39.239 | 56.047 |
| wide96 两次 | 126.777 | 49.355 | 77.422 |
| wide192 一次 | 124.274 | 58.276 | 65.998 |
| wide192 两次 | 177.226 | 80.688 | 96.539 |

回读函数计时包含 staging 创建、复制提交、等待先前 GPU 工作、映射与读取，不是纯 PCIe 传输或纯 GPU kernel 时间。表中差值包含 RHS 上传、命令编码、提交、解映射及原方程审核，尚未细分，也不能作为严格隔离的 CPU 时间。

结合每次上千个 dispatch、每个 dispatch 单独 compute pass 的实现，可以推断主机命令组织值得优先测量；现有数据不能判定唯一瓶颈。下一步建议分别测命令编码／提交、GPU 时间戳和原方程审核，再判断是否融合 kernel 或调整 pass；本轮没有实施这些改动。

运行前 GPU 为 P8／35°C，结束快照为 P0／39°C；只有首尾快照，不能证明全过程频率固定。没有因为换用较新 GPU 而宣称接近实时预算。
